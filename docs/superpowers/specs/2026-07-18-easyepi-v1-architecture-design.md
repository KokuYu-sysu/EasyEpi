# EasyEpi v1.0 总体架构设计

> 日期：2026-07-18  
> 状态：已批准  
> 决策依据：`docs/PRD.md`、`docs/TECH_STACK.md`、`docs/UI_DESIGN.md`、`docs/IMPLEMENTATION_PLAN.md`、`docs/PROJECT_DECISIONS.md`

## 1. 目标与交付边界

EasyEpi v1.0 是一款面向现场流行病学调查和临床研究的 Windows 离线桌面应用。最终交付物是适用于 Windows 10/11 x64 的 NSIS 安装版 `.exe` 和免安装便携版 `.exe`。

v1.0 包含问卷设计、字段校验、条件跳题、Key、加密项目保存、一问一屏录入、断点续录、数据管理、CSV 导出、基线表、EpiData 导入、衍生变量、数据质量检查、双录入验证及备份恢复。当前版本不包含云同步、多人实时协作、在线问卷分发、Excel/Word/PDF 导出、自动下载安装更新或 macOS 支持。

本规格定义全局架构与跨模块契约。项目采用纵向里程碑实施，每个里程碑另有独立实施计划并产出可运行、可测试、可打包的软件；不会用一个不可验收的巨型计划同时实现全部子系统。

## 2. 质量目标

- 完全离线运行，不上传调查数据，不采集遥测。
- 所有问卷答案及可能包含敏感信息的业务结构均加密存储。
- 在 10,000 份答卷规模下，管理页面仍能流畅分页、筛选和浏览。
- 支持 1366 × 768 及以上窗口，提供浅色、深色、大字体和键盘操作。
- 每个里程碑均通过 lint、类型检查、单元测试、集成测试和构建检查。
- 正式发布前通过完整 E2E 与 Windows 安装包冒烟测试。

## 3. 技术架构

应用采用 Electron 模块化单体架构：

- **主进程**：窗口生命周期、文件系统、加密、持久化、导入导出、统计、备份。
- **Preload**：通过 `contextBridge` 暴露最小化、强类型 API；不暴露 Node.js 原语。
- **渲染进程**：React 页面、组件、路由和交互；不得直接读取文件、数据库或密钥。
- **共享层**：领域类型、IPC 请求/响应、错误码及运行时验证 schema。
- **状态管理**：Zustand 保存界面状态和当前工作副本，主进程持久化结果是事实来源。

Electron 窗口必须启用 `contextIsolation`、禁用 `nodeIntegration`，并限制导航、外部窗口和非预期资源加载。

## 4. 模块边界

### 4.1 项目与问卷

- `project`：创建、打开、锁定、保存、格式版本和迁移。
- `questionnaire`：题目、选项、约束、排序、单一或复合 Key。
- `logic`：条件表达式、显示/跳过/必填动作、冲突检测。

问卷领域模型不依赖 React 或 Electron，可在纯 TypeScript 单元测试中运行。题目变量名在项目内唯一；Key 字段自动必填；规则只能引用当前项目中存在的题目。

### 4.2 录入与记录

- `entry`：一问一屏导航、校验、草稿、续录、提交和工作循环。
- `records`：答卷分页查询、筛选、编辑、删除和 Key 唯一性检查。

提交顺序固定为：字段校验 → 条件规则计算 → Key 唯一性 → 衍生变量计算 → 构造完整记录 → 加密原子写入。任一步骤失败都不得留下半条记录。

### 4.3 数据使用

- `export`：CSV、数据字典、多选题多分类/独热/哑变量编码。
- `baseline`：变量分类、描述性统计和基线特征表。
- `quality`：缺失、范围异常、逻辑矛盾、重复 Key 和双录入差异。

CSV 使用 UTF-8 BOM。基线表支持 CSV 导出和复制为 Markdown，不生成 Excel、Word 或 PDF。

### 4.4 兼容与计算

- `epidata`：`.qes` / `.rec` 格式识别、解析、预览和手工映射修正。
- `derived`：公式解析、类型检查、安全求值和依赖排序。

EpiData 解析遵循保守原则：不能可靠识别时返回带文件位置的错误，不猜测字段含义，不静默丢弃数据。当前以自建 fixtures 开发；真实样本兼容性在获得脱敏样本后作为独立验收项。

公式引擎只执行自定义 AST，不调用 `eval`、`Function` 或任意 JavaScript。循环依赖、未知变量、除零和类型不匹配必须在保存公式前报告。

### 4.5 安全与恢复

- `security`：管理员密码验证、密钥派生、恢复密钥、项目锁定。
- `backup`：原子写入、定时备份、版本保留和恢复。

密码哈希与数据加密密钥派生使用独立随机盐。敏感数据使用 AES-256-GCM，每次加密使用独立随机 IV。密钥仅存在于主进程内存中，项目锁定和应用退出时释放引用并尽可能清理缓冲区。

创建项目时显示一次恢复密钥，要求用户确认已保存。无密码或恢复密钥时不能绕过加密。日志不得记录答案、密码、密钥、恢复密钥或身份字段。

## 5. 数据与文件格式

每个项目位于用户选择的独立目录：

```text
项目目录/
├── project.easyepi
├── records.easyepi_data
├── metadata.easyepi_db
└── backups/
```

- `project.easyepi`：加密的问卷、规则、Key、衍生变量和项目设置。
- `records.easyepi_data`：加密的答卷记录。
- `metadata.easyepi_db`：格式版本、非敏感索引、迁移记录和性能索引；不得保存答卷明文。
- `backups/`：带时间和格式版本的加密快照。

所有自定义文件具有固定 magic、格式版本和完整性验证信息。写入流程为：在同目录创建临时文件 → 写入并同步 → 重新读取验证 → 原子替换正式文件。失败时保留旧文件并清理可安全识别的临时文件。

应用级偏好、最近项目路径和窗口设置保存在 Electron `userData` 目录，不包含答案或解密密钥。

## 6. IPC 契约

IPC 按领域命名，例如 `project:create`、`entry:submit`、`export:csv`。每个处理器必须：

1. 使用共享 schema 验证输入。
2. 验证项目会话和权限状态。
3. 调用单一领域服务。
4. 将内部异常转换为稳定的应用错误。
5. 返回可序列化的类型化结果。

渲染进程不接收原始密钥、数据库连接、Node.js `Buffer` 句柄或任意文件系统能力。文件选择由主进程对话框完成，渲染进程只获得用户已授权的路径或已解析结果。

## 7. 错误模型与用户反馈

应用错误至少区分：输入无效、密码错误、会话锁定、Key 重复、文件不存在、文件损坏、格式不支持、版本不兼容、导入解析失败、磁盘写入失败和未知内部错误。

- 字段错误就地显示，并把焦点移动到首个错误控件。
- 可恢复的业务错误使用页面消息或 Toast，不终止应用。
- 破坏性操作使用二次确认；删除记录还要求管理员会话有效。
- 文件损坏或版本不兼容时禁止覆盖原文件，并提供备份恢复入口。
- 导入错误提供文件、行/偏移、字段和原因；预览确认前不写入项目。
- 未知错误显示关联 ID，日志只记录去敏技术上下文。

## 8. 用户界面结构

渲染进程包含欢迎页、问卷设计页、EpiData 导入页、录入页、工作循环页、管理员验证页、数据管理页、基线表页和衍生变量页。

设计遵循 `docs/UI_DESIGN.md` 的颜色、字号、间距、圆角和交互规范。业务页面复用基础组件，不直接硬编码颜色或阴影。录入流程优先键盘效率；所有交互控件具有可见焦点和可读标签。

## 9. 测试与验证

所有功能遵循 RED → GREEN → REFACTOR：先写失败测试并确认失败原因，再写最小实现。

- **单元测试**：领域模型、校验、规则、加密、格式编码、解析器、统计和公式。
- **集成测试**：IPC、项目读写、数据库迁移、原子保存、备份恢复。
- **组件测试**：输入状态、错误反馈、键盘操作、主题和大字体。
- **E2E**：创建项目 → 设计 → 保存重开 → 录入续录 → 管理 → 导出。
- **兼容测试**：自建 EpiData fixtures；获得真实脱敏样本后追加回归。
- **打包测试**：安装版和便携版启动、创建项目、重启恢复及卸载。

核心安全和数据转换模块的分支覆盖率目标不低于 90%，整体单元测试覆盖率目标不低于 80%。覆盖率不是替代行为测试的验收条件。

## 10. 纵向里程碑

1. **M1 工程骨架**：安全 Electron 壳、React 页面、类型化 IPC、测试与 Windows 打包。
2. **M2 设计系统**：主题、基础组件、路由及关键页面骨架。
3. **M3 问卷可用**：问卷模型、规则、Key、设计器和加密项目保存。
4. **M4 录入可用**：一问一屏、草稿、续录、提交和工作循环。
5. **M5 数据可用**：管理后台、CSV、多选编码和基线表。
6. **M6 兼容可用**：EpiData 导入、预览及映射修正。
7. **M7 高级功能**：衍生变量、质量检查、双录入和完整备份恢复。
8. **M8 发布**：安全审查、10,000 记录性能验证、回归、安装版与便携版 `.exe`。

每个里程碑必须保持 `lint`、`typecheck`、测试和构建通过，并生成内部可运行产物。里程碑实现细节由对应实施计划约束。

## 11. Git 与可追溯性

- `master` 始终保持可构建。
- 使用 Conventional Commits。
- 每个可验证任务独立提交，提交信息说明行为变化。
- 需求和架构变化先更新决策或规格文档，再提交实现。
- 每个里程碑创建内部标签，例如 `v0.1.0-m1`。
- 默认只维护本地 Git，不创建或推送远程仓库。

## 12. 发布约束与已知风险

- 开发阶段使用临时应用图标，正式发布前替换。
- 当前无 Windows 代码签名证书，生成的测试安装包会显示未知发布者。
- 当前无真实脱敏 EpiData 样本，格式兼容性不能宣称完成实证验证。
- 当前无更新服务器或 GitHub 发布地址，仅保留手动检查更新入口，不自动下载安装。

这些事项不阻塞 M1–M7 开发；M8 发布验收必须明确记录图标、签名和真实 EpiData 验证的最终状态。
